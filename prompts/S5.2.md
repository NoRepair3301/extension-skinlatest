# S5.2 — Implement F1: clicking a theme applies it at once

Implements the design written in S5.1 (`workflow/F1_DESIGN.md`) and decision D5: a click on any of the 6 themes (or Auto) applies it to the current tab immediately, saves the choice, remembers the site (asking for the site permission inside the same click when needed), un-pauses a restored site, and re-themes without stacking. There is no separate Apply control. "Change my page" (the AI flow) stays as it is.

- **Model:** Opus 5.5
- **Effort:** high
- **Why:** user-gesture and permission ordering, script injection, per-site memory and re-theming across frames are easy to get subtly wrong, and a mistake shows up as "sometimes nothing happens" or stacked themes.

## Required behaviour (acceptance; all must be covered by tests)
1. Clicking a theme applies it to the current tab at once, with no other click. The popup shows a busy state while applying and the selected state when done.
2. The first `await` in the click handler is the permission request when one is needed (user-gesture rule); the order of calls follows design section 3. Permission denied leaves the page, settings and site record untouched and shows the message key from the design.
3. The choice is saved (`settings.theme` and the site record per design section 5) and the site is remembered, so the auto path re-applies it on the next page load.
4. Clicking a different theme replaces the old one with no stacked sheets, markers or leftover inline writes, in the main frame and same-origin frames; clicking the same theme again is a harmless no-op or refresh; rapid clicks end in the last theme.
5. A restored/paused site is un-paused by a theme click (design section 6).
6. The fresh-instance path no longer stacks on leftovers (the S2.3 gap near `applier-core.ts:93`): a test applies with instance A, drops A without restore, applies a different theme with instance B, then restores, and asserts the DOM equals the original (D12).
7. Ineligible pages (chrome://, store pages, PDF viewer, file:// without access, no host access) do nothing destructive and show the design's message.
8. Restore (button and Alt+Shift+R shortcut as they exist) still returns the page to its exact original after any sequence of theme clicks.
9. "Change my page" and the AI plan flow behave exactly as before, and a theme click and an AI plan on the same site coexist as the design specifies.
10. No permission, dependency or storage-key name is added or changed.

## Manual test (put these in HANDOFF; run before committing)
1. `npm run build`, reload the extension, open a normal site (Wikipedia). Open the popup and click a theme: the page themes at once, no second click.
2. Click each of the other themes in turn: each replaces the previous one; nothing stacks or flashes the old theme.
3. Click Auto, then a theme again.
4. Press Restore, then run `document.documentElement.outerHTML === window.__a` if you saved `window.__a` before theming; expect `true`.
5. After Restore click a theme again: it applies (un-pause).
6. Reload the page: the remembered theme comes back by itself.
7. On a site you never granted, click a theme: the permission prompt appears in the same click; deny it: the page is untouched and a message shows; allow it: the theme applies.
8. Open a `chrome://extensions` tab and click a theme: no error, a clear message.
9. Try "Change my page" once (if you have an AI key): it behaves as before.
10. No red errors in the page or service-worker console.
