## Work items (all five are required)

**1. I5 re-basing.** Today `put()` on an existing entry keeps `o/p` and overwrites `m`. If, since the engine's last write, the page changed that property (current value is not `m`, or priority is not `important`), the page wins: re-base the entry (`o,p` := the page's current value/priority) before writing the new themed value. Net effect required: after any number of refreshes, `restore()` yields the **page's latest** value for a property the page changed, and the original value for properties it never changed. Check every path that reaches `put()` (initial apply, `refreshBatch` via `reset`+`put`, hover/focus refresh, re-apply with a new theme). Where `refreshBatch` already re-bases through `reset()` then `put()`, prove it with a test rather than adding a second mechanism. Keep one clear mechanism; no duplicate logic.

**2. `suppressTransition` / `restoreTransitions` write outside the ledger (I2).** Route them through the ledger (or an equivalent that provably restores exactly), or avoid inline writes altogether. Required observable result: an element that had no `style` attribute and was refreshed by a class-change mutation ends `restore()` with **no** `style` attribute (today it can end with `style=""`); an element with an original `transition` returns to it exactly; the temporary `transition` override is never left behind and never survives into the page's own transition after the refresh. D12/I11 still hold: text restore only in final `restore()`, never in the refresh path.

**3. Realm check in `restore()`.** `instanceof win.HTMLElement` against the top window skips marked elements living in same-origin iframe documents. Replace with a realm-safe check (for example `el.nodeType === 1 && "style" in el`, or the element's own `ownerDocument.defaultView`). Test with a same-origin iframe document in jsdom: a themed element inside it is fully restored.

**4. `carriedText` retention.** It is a strong `Map<Element, string>` that lives until the next `restore()`. Remove the retention hazard: fold the carried text into the element record or tie it to the same lifetime/set as `modifiedElements`, so that nothing is held after the element is no longer tracked and nothing is held after `restore()`. Test: after `restore()`, no internal map/set holds elements (assert through observable behaviour, for example via a second `restore()` doing nothing, and a module-internal size check only if the file already exposes one; do not add exports).

**5. Deterministic refresh tests.** Replace the fixed 20 ms wait in the refresh-path test with a deterministic mechanism (fake timers plus explicit flush, or `MutationObserver.takeRecords()` plus the engine's own scheduler hooks as the existing tests do). No `setTimeout(…, <number>)` real-time waits in the engine tests you touch.
