## Required behaviour

**1. Test: the auto path reaches the engine (T5).** Using jsdom and the real `createApplier`/`applyTokens` (no mocking of the engine), simulate the auto flow: a stored site plan, `runAuto` called with the applier present. Assert observable engine effects, not just that a function was called: the engine marker attribute (use the exported marker constant from the engine, not a literal) appears on themed elements, the engine's inline properties are written, and `restore()` through the same applier returns the page to its exact original inline state. Also assert that `runAuto` does not use the old structural path (no compiled structural stylesheet is injected; if you cannot assert this cleanly from observable output, say so in HANDOFF rather than inventing a fragile assertion).

**2. Fail-safe when the applier is missing.** If `applier-auto` runs and the applier global is absent (script order wrong, applier failed to inject, extension reload), it must: not throw, not leave any marker/attribute/stylesheet behind, never hide or blank the page (I1), and log at most one concise `console.warn`. If this already holds, add the test and change no source. If it does not hold, make the smallest guard in `applier-auto.ts`/`auto-core.ts`; no refactor. Test both "applier global undefined" and "applier present but `applyTokens` throws": in the second case the page must be left untouched (the engine's own restore must run or nothing must have been written) and the error must not escape.

**3. `validate-dist` assertions.** Add (or adjust) checks that run on the built output:
- `dist/applier.js` contains the engine marker string (one literal, defined once at the top of the script with a comment that the Stage 6 rename changes it to `data-repaint-engine`; the marker string today is `data-skinly-engine`).
- `dist/applier-auto.js` does **not** contain the marker string and does not contain the engine's base-sheet signature constant from S2.3 (read the signature from `src/engine/dom.ts`; if it is a plain string literal, assert on it; otherwise assert on the marker only and say so).
- If `validate-dist` previously required the marker in both bundles, remove that requirement (D9) and note it in DECISIONS.
Keep all other existing assertions as they are. The script must exit non-zero with a clear message when an assertion fails.

**4. Rebuild and verify.** Run `npm run build` then `npm run validate-dist`; report the results. Prove the new `validate-dist` checks bite: temporarily (in a scratch copy or by running the check function against a doctored string, not by editing `dist` by hand) show that a bundle missing the marker and a bundle containing it twice in the wrong file would be rejected. Do not leave any temporary file in the repo.
