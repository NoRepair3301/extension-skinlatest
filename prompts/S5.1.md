# S5.1 — F1 design only: clicking a theme applies it (no code)

Stage 5 delivers F1: **clicking a theme in the popup applies it to the whole page immediately, with no separate Apply button.** Per decision D5: the click applies that built-in theme to the current tab at once, saves the choice, remembers the site (asking for the site permission inside the same click if needed), and un-pauses a site the user had restored. The AI flow stays behind "Change my page", unchanged. This substage writes the design only. It changes no source file, so S5.2 can implement it without guessing.

## Session settings
- **Model:** Opus 5.5
- **Effort:** high
- **Why:** the hard part is the interplay of user-gesture rules, host permissions, script injection, per-site memory, pause/un-pause and re-theming without stacking. A design error here becomes a flaky feature later.

## What the design must contain (sections in this order)
1. **Current behaviour map.** Today's flows with file:line: what the theme radios do now, what "Change my page" does, what restore and auto-apply do. A short table of the states a tab/site can be in: never themed, themed, themed+remembered, restored/paused, ineligible (chrome://, store pages, PDF viewer, file:// without access), permission missing, applier not injected.
2. **Target behaviour, event by event.** For each of: click a theme on an eligible themed tab; click the same theme again; click a different theme (re-theme without stacking); click "Auto"; click a theme on a restored/paused site (un-pause); click a theme on a site without permission; click on an ineligible page; click while a previous apply is still running (rapid clicks); popup closes mid-apply. For each: the exact sequence of calls, which call runs inside the user gesture, what is stored, what the page ends as, and what the popup shows.
3. **Gesture and permission handling.** Chrome requires `permissions.request` to be called synchronously inside the click gesture, before any other `await`. State precisely how the handler is ordered so the permission prompt works, how `activeTab` / host permission are used for injection, and what happens on deny. Say what the "remember this site" step needs and when it can be skipped (already granted).
4. **Re-theme without stacking.** Specify exactly how a new theme replaces an old one on the same page (and across same-origin frames): reuse the live engine instance when present (refresh/replace theme through the engine), or full restore then apply when a fresh instance finds leftovers. Settle the S2.3 gap: the fresh-instance path must run the marker cleanup (or an equivalent) before applying, and say where. Include the ledger and invariant implications (I2 to I7, D12): what the page-owned originals are after the swap.
5. **Persistence.** What is written when a theme is clicked (`settings.theme`, site record, remembered flag, pause flag), in what order, and what a failure in the middle leaves behind. Interaction with the keeper's per-origin registration and the auto path on the next page load. How "Auto" is stored and resolved.
6. **Un-pause and restore interplay.** After Restore the site is paused; define precisely what clicking a theme does to that state, and what the popup shows after restore (F2 UX is S5.3, but the state model is decided here).
7. **Popup UI changes.** Which elements disappear (any separate Apply control, if one exists in the code), selected-state semantics for the radios (current theme of this tab/site vs global default), busy and error indication, keyboard/ARIA behaviour. No visual redesign beyond that; reuse existing strings where possible and list the new strings needed (S5.4 owns their final copy).
8. **AI flow isolation.** Show that "Change my page" and its pending-intent plumbing are untouched, and how a theme click and an AI plan on the same site coexist (which one wins, how the site record represents each).
9. **Error and edge states** for S5.4: a table of conditions with the intended message key and recovery.
10. **Test plan for S5.2 and S5.3.** The concrete tests (names and what each asserts), at the right layer (port/API logic with fakes, popup component, integration with jsdom and the real applier), including: click applies without any second action; same-site rapid clicks end in the last theme; swap leaves no stacked sheets or markers; permission denied leaves the page untouched and shows the message; un-pause; restore after swap is exact (D12).
11. **Implementation plan.** An ordered list of changes for S5.2 (files and functions, with what each does) and what is left to S5.3 and S5.4, each small enough for one session.
12. **Risks and open questions.** Anything uncertain; for each, a recommended default. Separate "owner must decide" items (few, concrete, yes/no) from "implementer decides" items.
