## Step 1 — classify before deleting
Produce `workflow/TEST_CLASSIFICATION.md` first, as a table covering every test file that imports (directly or transitively through helpers) any of: the plan compiler (`plan/compile`), layouts, compat rules, golden CSS, the structural fixtures runner, or checks `data-skinly-r` region tagging / compiled stylesheet output. Columns: file | tests (count) | what it checks | imports of structural modules (evidence) | verdict | reason.

Verdicts:
- **DELETE** — the test only checks the old structural compile/layout/compat/golden output. Condition: the module it exercises no longer runs in the apply path (state the evidence, for example "`compileCss` has no caller: grep result"), and the user-visible behaviour it protected is either gone by design or covered by an engine test (name it).
- **ADAPT** — the test protects behaviour that still exists (an invariant on the DOM, a safety property); rewrite it to run against the engine.
- **LEAVE** — not in this substage's scope (guard, rules, flow-safety, restore-markers, anything protected): list it with the substage that owns it (S3.2 for guard/rules/flow-safety, S3.4 for residuals).
- **BUG** — an invariant that the engine really violates. Do not fix `src/`; keep the test, mark it clearly, and report it.
If a file mixes structural and live tests, split it: delete only the structural cases and keep the rest untouched. Any file you cannot classify with evidence is LEAVE, not DELETE.

Delete the DELETE-verdict files/cases. After each group, run `npm run gate -- --only vitest` quickly (or the affected files) to confirm you did not break an unrelated test. Do not delete a source module; if the source now has zero importers, just list it for S3.3 in HANDOFF.

## Step 3 — adapt
1. `tests/applier.test.ts` "tags regions with data-skinly-r only": the built-in theme plan has no region rules, so nothing is tagged under the engine. Decide from evidence: if region tagging (`data-skinly-r`) still has a live purpose in `applier-core.ts` for another feature, adapt the test to a plan that does produce regions; if the tagging is dead for built-in themes, rewrite the test to assert what the applier now guarantees (themed elements carry only the engine marker, no `data-skinly-r`) and state this in DECISIONS.
2. `tests/legacy.test.ts` (7 failing invariants): for each, decide ADAPT / DELETE / BUG with evidence.
   - "no attribute other than `data-skinly-*`" style invariants: rewrite to the engine's real guarantee: while themed, the only attribute changes on page elements are the engine marker and `style`; after `restore()` the DOM is identical to the original (`outerHTML` equality on the fixture, I6/D12), including `td[bgcolor]`-style legacy attributes.
   - "compiled sheet lacks `td[bgcolor]`": the engine themes from computed style, so assert that an element with a legacy `bgcolor` attribute ends up with an engine-written background and restores exactly; do not reinstate a structural selector.
   - Keep each adapted test's name and intent recognisable; add the invariant id (for example `I6`, `D12`) to the name.
Every adapted test must still fail if the behaviour breaks: for each, show one deliberate breakage in a scratch copy (not committed, not in `src/`) or explain precisely why it would fail, and say which you verified in HANDOFF.
