## Step 1 — classify

Columns: file | test name | what property it protects | does that property still exist in the engine world? (evidence) | verdict | reason.
Verdicts:
- **DELETE** — protects only the old structural output (compiled repair sheets, step-down repair rules, `data-skinly-*` repair selectors). Evidence required: the code path it exercises has no caller in `src/` (grep result), and the user-visible promise is either gone by design (D6, aiRepair removed) or covered by an engine test (name it).

- **LEAVE** — out of this substage; name the owner substage.
A test whose evidence you cannot produce is not DELETE.

## Step 2 — investigate two specific items
1. **Guard "re-render" case** (in `tests/guard.test.ts`; the recon flagged it as needing a look). Establish what promise it protects: when the page re-renders content (an element is replaced, re-inserted or its classes change), the new content must be themed again and its text must stay at or above the contrast floor (>= 4.5, or >= 7 for high-contrast; I10). Check how the engine's observer handles this today. Then write an engine-level test (in the case's file or in `tests/engine/rerender.test.ts`) for: replaced node, re-inserted node, class change, and a node added inside an open shadow root. If it passes, the case is ADAPT. If the engine leaves any of them unthemed or below the floor, it is a **BUG**: keep a failing test and write the reproduction steps in HANDOFF.
2. **Stored-repair test** (`tests/restore-markers.test.ts`). The S2.3 session found that `applier-core.ts` around lines 122-124 adds stored repair CSS (`repairCss`) to the page without the validity check that S1.2 removed along with aiRepair. Read `git log -p --ignore-cr-at-eol -S"repairCss" -- src/extension/applier-core.ts` and the S1.2 diff to see exactly what was removed. Then decide and document: (a) is `repairCss` still produced by anything today, or only present in already-stored site records from older versions? (b) is unvalidated stored CSS being injected into pages a security or CSP regression compared with before S1.2? (c) what is the smallest correct fix (for example: restore the removed check, or stop applying stored repair CSS and drop the field on migration)? Do not change `src/`. Put your recommendation, with the exact diff, in `workflow/S3.2_PROPOSED.patch` and HANDOFF, and mark the test BUG if the current behaviour is unsafe; otherwise decide whether the test is DELETE (the injected sheet no longer exists by design) or ADAPT.
