# S3.5 — Engine bug B: contrast must be measured against the effective backdrop

Real defect found in S3.2 (reproductions in `workflow/HANDOFF.md`, S3.2 section; the failing tests are marked BUG in `workflow/TEST_CLASSIFICATION.md`). Today the engine measures text contrast against the **theme background** only. Light text on dark buttons, banners and hero pictures therefore ends around 3:1 or turns grey. The bug B tests are this substage's acceptance tests. Bugs A and C were fixed in S3.4 and must not regress.

It needs a correct model of what is actually behind each piece of text (nested, semi-transparent, gradient and image backdrops), a processing order that keeps ancestors before descendants, and a refresh story that stays inside the ledger invariants.

## Required behaviour
**1. Model the effective backdrop.** For every piece of text the engine recolours, determine the colour actually behind it, then choose the text colour so the ratio meets the floor (>= 4.5, or >= 7 for high-contrast; I10) against **that**, not against the theme background. Cases to handle and to document in DECISIONS:
- Element's own opaque background (after theming, since the engine may recolour backgrounds) or an ancestor's, nearest first.
- Semi-transparent backgrounds: composite over what is behind them, walking up to the root, with the theme background as the final base.
- Backdrops the engine does not recolour (I8 and the known limitation "no `url()` backgrounds"): `background-image` with `url()`, gradients, media behind text. Estimate the backdrop luminance in a defensible way and write down the rule. Suggested approach: for gradients use the stops (worst case against the text colour); for `url()` images, which cannot be sampled, infer from the page's own original text colour (light original text implies a dark image behind it, dark implies light) and keep the text on the correct side of the luminance range, never flipping it to the theme's default. If a better approach exists, use it, with reasons.
- Text inside the engine's skipped/inherited elements (the S3.4 logic): the inherited value must still meet the floor against the child's own effective backdrop; if not, the child must be written.
**2. Ordering and refresh.** Ancestors' resolved backgrounds must be known before descendants' text is decided. When an ancestor's background changes (page change, theme change, hover or focus state, class change), affected descendants are recomputed. No quadratic walks: cache the resolved backdrop per element within a batch and invalidate on change; state the complexity and report timing on a fixture with a few thousand nodes before and after.
**3. Invariants.** I1 (never hide the page), I2-I6 and D12/I11 (ledger, exact restore, page-wins re-basing), I7 (no self-triggered observer, no timers left), I8 (media never recoloured), I10 (floors). The S3.4 behaviours (skip logic, late shadow roots) keep passing. Light themes must not regress on ordinary pages: text on ordinary white or theme-coloured backgrounds keeps the colours it gets today unless the floor requires a change; do not make every page grey.
**4. What not to do.** No sampling via canvas or network, no reading image pixels, no `visibility:hidden`/overlay tricks, no new permissions, no new dependencies.
