## Bug A — a colour equal to its parent's is skipped
Symptom: on pages that set the text colour once on `html, body` (very common), light themes can end at 1.0:1 contrast (text colour equals background). First establish the root cause from the code and the failing test, in your own words, before changing anything: where does `dom.ts` decide to skip an element whose computed colour equals its parent's, and what does it assume about the parent? (Likely assumption to check: "the child inherits the parent's *themed* value, so no write is needed", which is false if the parent itself was skipped, written differently, is the root element, or is outside the engine's reach.)
Requirements for the fix:
- A skipped element must still end with the **themed** colour at or above the contrast floor (>= 4.5, or >= 7 for high-contrast; I10). Keep the optimisation only where it is provably correct (the parent's *written* value is what the child inherits, and the child has no own rule changing it); otherwise write.
- Applies to `color` and any other property that uses the same skip logic (check `background-color`, borders and custom properties; do not widen scope to new properties).
- I2/I3/I4: every write goes through the ledger; restore is exact; D12/I11 unchanged; the refresh path (`refreshBatch`, hover/focus) must behave the same for skipped and written elements (a child that was skipped must become written when its parent's themed value changes, and vice versa, without stale records).
- Performance: report the number of inline writes on a representative fixture before and after; a large increase must be justified or reduced.

## Bug C — a shadow root attached after apply is never watched
Symptom: web components that call `attachShadow({mode: "open"})` after the engine applied (lazy components, frameworks) stay unthemed, and later changes inside them are not observed. Establish what the engine does today for roots present at apply time (scan + observer per root) and what signals exist for a late attachment: attaching a shadow root fires no mutation on the host, and in the extension's isolated world you cannot patch the page's `attachShadow`. Choose a design that is bounded and safe, and record it in DECISIONS. Candidates to consider (you decide, with reasons): (1) when the observer reports added nodes, scan the added subtree for hosts whose `shadowRoot` is open and not yet watched; (2) re-check known custom-element hosts (tag name with a hyphen) on the existing refresh triggers (hover/focus/mutation batches) rather than a timer; (3) `customElements.whenDefined` for undefined custom elements already in the page. Hard requirements:
- No polling timers or intervals left behind (I7); no new timers surviving `restore()`.
- The engine's own writes never trigger the scan (`quiet()`); no feedback loop; cost per mutation batch stays proportional to the number of added nodes.
- Each late root is observed and themed exactly once; `restore()` stops observing it and restores everything inside it exactly; fresh-instance cleanup (S2.3) also cleans late roots (verify with a test; fix only if it fails).
- Closed roots stay a documented limitation. Same-origin iframes keep working.
