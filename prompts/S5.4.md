## Required behaviour
1. **One message per condition, no raw errors.** Implement every row of the design's section 9 table. At minimum: ineligible page (chrome://, edge://, extension pages, Web Store, PDF viewer, `about:`, `file://` without file access), host permission not granted, permission denied by the user, injection failed, applier missing or unresponsive after a timeout, theme apply failed midway, restore failed, tab closed or navigated away during apply, storage write failed. Each has a distinct, plain-language string with a recovery hint (for example how to allow file access) in the same voice as existing strings. No stack traces, error codes or the words "undefined"/"null" reach the user.
2. **Progress and busy.** While applying or restoring, the control that was clicked shows a busy state, other theme clicks queue or are coalesced per the design (last click wins), and the popup never gets stuck: every busy state has a timeout path that ends in a message and an enabled UI.
3. **State consistency.** After any failure the UI, the stored settings and the page agree: a failed apply leaves no stored "themed" state and no half-applied page; a failed restore keeps Restore enabled and says so; a denied permission leaves the previous theme selection displayed.
4. **Accessibility.** Messages are in a polite live region, errors are associated with the control, focus is not trapped or lost, colours of messages meet contrast in the popup's own themes.
5. **Strings hygiene.** All new copy lives in the strings module (no inline literals in components), each key has a short comment about when it appears, none mentions Plus/plans/accounts, and the product name is spelled exactly as it is in the code today (renaming is Stage 6).
6. No new permissions, dependencies or storage keys.
